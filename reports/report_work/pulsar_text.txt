P43 [Heading 1] ABSTRACT
P44 [Normal] Medical image classification research increasingly explores distributed learning methods that allow multiple data holders to contribute to a shared model without routinely transferring their raw training images to a central repository. This course project presents PULSAR, a research-oriented application for lung image classification and federated learning experimentation. The system combines a doctor-oriented patient-record workflow, image-based classification, Grad-CAM visual explanations, and a research pipeline for comparing centralized and federated model training.
P45 [Normal] The application uses a single ResNet18 convolutional neural network with a four-class output layer. Centralized training, Federated Averaging (FedAvg), and Federated Proximal (FedProx) are treated as different training strategies using the same model architecture. Federated experiments use three simulated hospital clients with non-identically distributed data partitions. Flower provides the federated orchestration and secure aggregation workflow. An experimental Opacus-based DP-SGD path applies per-sample gradient processing, clipping, noise, and Rényi Differential Privacy accounting within the documented mechanism scope. The application includes React-based Admin and Doctor workspaces, a FastAPI backend, SQLite persistence, protected image/report access, and a separate worker for long-running experiments.
P46 [Normal] The selected inference checkpoint achieved 75.68% accuracy, corresponding to 84 correct predictions among 111 held-out images in the documented evaluation. This is an aggregate result on a particular test set and must not be interpreted as the probability that an individual patient has cancer. A separate one-round secure verification experiment recorded 36.04% accuracy; it is a distinct experiment and is not the active model's accuracy. The project is a local research prototype using simulated clients. It has not established clinical validity, regulatory approval, deployment across independent hospitals, or a production privacy guarantee against every adversary.
P47 [Normal] The project demonstrates an integrated implementation of image classification, federated optimization, secure aggregation, experimental differential privacy, explainability, and application-level access controls. Further work requires patient-independent and external validation, larger and better-documented datasets, multi-host deployment, independent security review, and a complete production privacy policy.

P63 [Heading 2] 1.2 Problem Statement
P64 [Normal] Medical institutions may hold sensitive image datasets that cannot be freely pooled because of privacy, governance, operational, and institutional constraints. A conventional centralized machine-learning workflow requires data to be collected at one location before training. This can create data-transfer and data-governance challenges, particularly when the data originates from multiple hospitals.
P65 [Normal] Federated learning offers an alternative training arrangement in which participating clients retain their local training samples and communicate model updates or protocol messages to a coordinator. However, federated learning alone does not guarantee privacy. Individual model updates may reveal information, and a coordinator may gain access to more information than intended unless the aggregation protocol and threat model are considered.
P66 [Normal] Another challenge is that a classification result can be misunderstood as a confirmed medical diagnosis. Dataset-level accuracy does not measure certainty for an individual patient, and a visual explanation does not prove that a model has identified a tumour or clinically meaningful region. A reliable research prototype must therefore communicate its evaluation limits and separate image-model output from doctor-entered clinical observations.
P67 [Normal] The problem addressed by PULSAR is to implement and evaluate a local research system that supports lung-image classification and compares centralized and federated training while exploring secure aggregation and differential privacy as distinct protection mechanisms. The implementation must also provide controlled access to patient records and preserve a clear boundary between experimental outputs and clinical decisions.

P86 [Heading 1] CHAPTER 2: LITERATURE SURVEY
P87 [Heading 2] 2.1 Existing System and Its Limitations
P88 [Normal] Traditional centralized training collects training images in a single repository and optimizes a model over the pooled dataset. This arrangement can simplify data loading, model management, and evaluation. Its limitation in multi-institution settings is that it assumes the training data can be transferred and governed centrally. Such an assumption may not be suitable for every hospital or research collaboration.
P89 [Normal] Federated learning changes the training topology. A coordinator distributes a global model to participating clients; each client performs local optimization and returns an update; the coordinator aggregates the updates to form the next global model. FedAvg uses a sample-weighted average of client model parameters. FedProx adds a proximal term to the local objective to discourage excessive movement away from the current global parameters, which can be useful when client data distributions differ.
P90 [Normal] Basic federated learning does not automatically hide information contained in model updates. Secure aggregation addresses a different concern by allowing a coordinator to recover a permitted aggregate without directly inspecting each individual unmasked contribution, subject to protocol assumptions. Differential privacy is also distinct: it bounds the influence of individual records under a defined mechanism and accounting model. It requires explicit choices about the privacy unit, clipping, noise, sampling, composition, and randomness.
P91 [Normal] Image classifiers also have limitations beyond privacy. Their performance depends on dataset quality, label consistency, patient-level split isolation, image modality, preprocessing, class balance, and external representativeness. A model may achieve a particular test accuracy while still failing to generalize to a new hospital or patient population. Grad-CAM can provide a visual indication of regions associated with a class score, but it is not a substitute for clinical interpretation.
P92 [Heading 2] 2.1 Existing System and Its Limitations (Continued)
P93 [Normal] Several practical limitations arise when these techniques are implemented without a complete application and evidence workflow. A model-training script alone does not provide authenticated access, patient ownership, protected image retrieval, experiment provenance, or reproducible reporting. Conversely, a polished interface does not prove that the underlying metrics are genuine or that the model was trained using the stated data partition.
P94 [Normal] PULSAR's implementation documentation records specific safeguards against these problems. The dataset workflow uses byte and pixel hashing, duplicate grouping, reproducible manifests, and checks for split overlap. Checkpoint loading validates metadata and class mapping instead of silently loading an incompatible model. The application also separates image-model results from doctor observations and removes retired combined/tabular risk paths.
P95 [Normal] The project records limitations rather than treating every technology as an absolute guarantee. The hospital clients share one host; the secure aggregation threat model excludes a host administrator and client collusion; DP-SGD is experimental and uses a documented limited mechanism; and external patient-independent validation is still required. These boundaries are part of the technical evaluation, not optional disclaimers.

P142 [Heading 2] 3.2 System Architecture – Federated Workflow
P143 [Normal] The federated workflow uses a coordinator and three local hospital client processes. At the beginning of a round, the coordinator provides the current global model parameters and protocol instructions. Each client performs local optimization using its own partition. The clients then return permitted update messages for aggregation.
P144 [Normal] In FedAvg, the coordinator computes a sample-weighted average of client model parameters. In FedProx, each client optimizes a local objective containing a proximal penalty relative to the received global parameters. This helps control client drift when local data distributions differ. The clients are simulated locally and share one machine and filesystem.
P145 [Normal] In the secure workflow, the Flower SecAgg+ stages coordinate key setup, masked update upload, and aggregate reconstruction. A cryptographic pseudorandom generator adapter expands protocol material into masks. The client modifier masks model arrays inside the client process and clears the unmasked array records before the reply crosses the process boundary. The coordinator strategy receives the reconstructed weighted aggregate, not the individual unmasked client models.
P146 [Normal] The documented threat model is limited. The clients share a host; a host administrator is outside the protection boundary; client collusion is not covered; and independent multi-host deployment has not been validated. These constraints must accompany any description of the secure aggregation feature.

P194 [Heading 2] 4.2 Flowchart – Application Workflow
P195 [Normal] The application workflow begins when a user opens the PULSAR web interface and authenticates. The backend validates the credentials and establishes a session. The application then loads the workspace associated with the user's role. Admins can manage doctor accounts and review aggregate experiment information; Doctors can manage their own patient records and clinical workflow.
P196 [Normal] During patient image analysis, the doctor selects an owned patient record and uploads a PNG or JPEG image. The backend validates the file and stores it in protected storage. The inference service loads the approved ResNet18 checkpoint, performs preprocessing and prediction, and stores the analysis result and associated metadata. Grad-CAM output is generated for visual review. The doctor may add observations and generate a PDF report.
P197 [Normal] During a research experiment, an authorized user submits a configuration. The backend creates a queued experiment record. The separate worker claims the job and starts centralized or federated training. For federated experiments, three local clients train on their partitions and the selected aggregation strategy updates the global model. Results, metrics, failures, and checkpoints are persisted for later review.

P199 [Heading 2] 4.2 Flowchart – Federated Experiment Workflow
P200 [Normal] The federated experiment flow starts with a validated experiment configuration and a reproducible dataset manifest. The coordinator initializes the global ResNet18 model and prepares the three simulated client partitions. In each round, the current global parameters are made available to the clients. Each client performs local optimization according to the selected strategy and local training configuration.
P201 [Normal] For a FedAvg run, the clients return model updates that are combined using sample-weighted aggregation. For FedProx, the local objective includes a proximal regularization term before aggregation. In a secure run, the SecAgg+ protocol coordinates the required setup and masked uploads; the coordinator reconstructs the permitted aggregate after protocol completion. If protocol thresholds or failure conditions are not met, the round aborts rather than fabricating an aggregate.
P202 [Normal] After aggregation, the global model is evaluated on the designated validation data and round metrics are recorded. The training engine tracks the best checkpoint according to the configured validation process. At completion, the experiment status, metrics, checkpoint, and artifacts are persisted. The selected application inference model changes only through the explicit model approval workflow.

P229 [Heading 1] CHAPTER 5: CONCLUSION AND FUTURE SCOPE
P230 [Heading 2] 5.1 Conclusion
P231 [Normal] PULSAR demonstrates an integrated research prototype for lung image classification and privacy-aware federated learning experimentation. The system combines a ResNet18 image classifier, Grad-CAM visualization, doctor-managed patient records, protected file handling, PDF reports, centralized and federated training, secure aggregation integration, experimental DP-SGD, and persistent experiment tracking.
P232 [Normal] The implementation uses a single ResNet18 architecture with a four-class output head. Centralized training, FedAvg, and FedProx are training approaches that use this common model family. Three simulated hospital clients perform local optimization on non-IID partitions. Flower SecAgg+ provides a secure aggregation workflow under a limited documented threat model, while Opacus supports an experimental DP-SGD mechanism with per-sample processing and RDP accounting.
P233 [Normal] The selected inference checkpoint achieved 75.68% accuracy, with 84 correct classifications among 111 held-out images. This result is specific to the documented test set and does not establish clinical diagnostic accuracy or individual patient certainty. A separate one-round secure verification experiment recorded 36.04% accuracy; it is not the active model's accuracy, and DP was disabled in that run.
P234 [Normal] The project also demonstrates application-level controls through Admin and Doctor roles, doctor-owned patient records, protected image and report retrieval, and experiment persistence. The recorded backend, browser, build, lint, and dataset-audit results provide evidence of local software verification. However, the clients are simulated on one machine, the privacy mechanisms have documented limits, and the model has not undergone external clinical validation.
P235 [Normal] Overall, the project meets its research-prototype objective by implementing and testing a connected application and federated learning workflow while documenting what remains unverified. It should be presented as a technical research and educational system, not as a clinically approved diagnostic tool.
P236 [Heading 2] 5.2 Future Scope
P237 [Normal] Future work should first strengthen dataset quality and evaluation. The project requires trusted patient/study identifiers, source and modality metadata, patient-independent grouped evaluation, review of related or near-duplicate scans, external dataset testing, uncertainty intervals, calibration analysis, and clinically meaningful error analysis. Model selection should use validation metrics, with test data reserved for final evaluation.
P238 [Normal] Predictive performance can be investigated through controlled experiments using justified augmentation, larger input resolution, pretrained initialization, learning-rate schedules, class-imbalance analysis, and hyperparameter search. Such changes must be trained and evaluated before any improvement is claimed. Centralized, FedAvg, FedProx, secure, and DP experiments should be compared under matched initialization, preprocessing, optimization budgets, data splits, and multiple random seeds where practical.
P239 [Normal] Federated deployment can be extended from local simulation to independently administered hosts. This requires authenticated inter-client transport, deployment and dropout testing across machines, concurrency and operations design, and independent review of the SecAgg+ integration and cryptographic PRG adapter. Stronger threat models may need to address client collusion and malicious servers.
P240 [Normal] The differential-privacy implementation requires production-grade randomness, an explicitly justified privacy unit, complete release and composition accounting, and a documented policy for all model releases and outputs. The project also requires PostgreSQL integration testing if a server database is adopted, TLS, at-rest encryption, backup and restore procedures, retention policies, identity/MFA controls as required, and a review of dataset and software licenses.
P241 [Normal] Finally, any move toward clinical use would require expert evaluation, appropriate institutional governance, regulatory assessment, usability testing, and prospective validation. Until those activities are completed, the application should remain a research prototype and should not be used to make independent patient-care decisions.
