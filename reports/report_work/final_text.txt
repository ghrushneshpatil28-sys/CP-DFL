ABSTRACT
Medical image classification research increasingly explores distributed learning methods that allow multiple data holders to contribute to a shared model without routinely transferring their raw training images to a central repository. This course project presents PULSAR, a research-oriented application for lung image classification and federated learning experimentation. The system combines a doctor-oriented patient-record workflow, image-based classification, Grad-CAM visual explanations, and a research pipeline for comparing centralized and federated model training.
The application uses a single ResNet18 convolutional neural network with a four-class output layer. Centralized training, Federated Averaging (FedAvg), and Federated Proximal (FedProx) are treated as different training strategies using the same model architecture. Federated experiments use three simulated hospital clients with non-identically distributed data partitions. Flower provides the federated orchestration and secure aggregation workflow. An experimental Opacus-based DP-SGD path applies per-sample gradient processing, clipping, noise, and Rényi Differential Privacy accounting within the documented mechanism scope. The application includes React-based Admin and Doctor workspaces, a FastAPI backend, SQLite persistence, protected image/report access, and a separate worker for long-running experiments.
The selected inference checkpoint achieved 75.68% accuracy, corresponding to 84 correct predictions among 111 held-out images in the documented evaluation. This is an aggregate result on a particular test set and must not be interpreted as the probability that an individual patient has cancer. A separate one-round secure verification experiment recorded 36.04% accuracy; it is a distinct experiment and is not the active model's accuracy. The project is a local research prototype using simulated clients. It has not established clinical validity, regulatory approval, deployment across independent hospitals, or a production privacy guarantee against every adversary.
The project demonstrates an integrated implementation of image classification, federated optimization, secure aggregation, experimental differential privacy, explainability, and application-level access controls. Further work requires patient-independent and external validation, larger and better-documented datasets, multi-host deployment, independent security review, and a complete production privacy policy.

CHAPTER 1  INTRODUCTION
1.1 Overview of the Project
PULSAR is a course-project research application for lung image classification and privacy-aware distributed training. It connects a doctor-facing image-analysis workflow, persistent patient records, and a learning pipeline that compares centralized and federated optimization. It is a local research prototype rather than a clinically approved diagnostic product.
ResNet18 is the single active classifier, with a four-class output head. Centralized training, Federated Averaging (FedAvg), and Federated Proximal (FedProx) are training strategies using this common architecture. Three simulated hospitals perform client-specific training. Flower SecAgg+ and experimental Opacus DP-SGD address different aspects of update protection.
Alongside the research pipeline, PULSAR provides Admin and Doctor roles. Doctors can manage patient records, record visits and follow-ups, upload supported images, review model output and Grad-CAM visualizations, add observations, and generate PDF reports. Admins manage doctor accounts and inspect aggregate application and experiment information. Patients are records in the system; they do not have login accounts.
1.2 Problem Statement
Medical institutions may hold image datasets that cannot be freely pooled because of privacy, governance, and operational constraints. Centralized training assumes pooled access; federated learning instead communicates model updates while keeping routine training-image processing local. Individual updates can still reveal information, so data locality alone does not establish privacy.
PULSAR addresses this problem by implementing and evaluating centralized and federated image classification, exploring secure aggregation and differential privacy separately, and integrating controlled access to patient records. Model class probabilities and Grad-CAM must remain distinct from confirmed diagnosis, patient-level certainty, and doctor-entered observations.
1.3 Objectives
The project aims to implement an integrated research prototype for lung image classification and controlled federated learning experiments. Its objectives are to:
1. Validate one four-class ResNet18 architecture and a strict checkpoint metadata contract.
2. Compare centralized, FedAvg, and FedProx training using a shared optimization and evaluation engine.
3. Simulate three hospitals with reproducible non-IID partitions, real local optimization, and aggregation.
4. Integrate Flower SecAgg+ and verify aggregate-only visibility at the documented coordinator boundary.
5. Implement experimental Opacus DP-SGD with clipping, noise, and cumulative RDP accounting.
6. Provide Grad-CAM visualizations and clearly communicate their interpretation limits.
7. Develop authenticated Admin and Doctor workflows, patient ownership, protected files, and PDF reports.
8. Persist experiment settings, round metrics, checkpoints, results, and failures.
1.4 Scope of the Project
The scope includes the React application, FastAPI backend, SQLite persistence, protected raster-image inference, Grad-CAM, centralized and federated training, secure aggregation, and experimental DP-SGD. Clients run as three hospital processes on one local machine. This demonstrates training and protocol behavior, not independently administered multi-hospital deployment or protection against the shared-host administrator.
The model predicts one of four dataset labels from a supported image. It does not perform cancer staging, tumour segmentation, treatment recommendation, clinical-risk fusion, or automatic diagnosis. Doctor-entered medical history and observations are stored for record keeping and review and are not secretly combined with image probabilities to generate another score.
Clinical deployment, regulatory approval, validated DICOM processing, external validation, and production privacy governance remain outside the verified scope.
CHAPTER 2  LITERATURE SURVEY
2.1 Background and Related Concepts
2.1.1 Residual Learning and Medical Images
Residual networks learn transformations through blocks with shortcut connections. ResNet18 provides the common image-classification architecture used throughout PULSAR. The final fully connected layer produces four class scores. Model architecture and training strategy are separate choices: a centralized run, FedAvg run, and FedProx run can all use the same ResNet18 network. The project uses the torchvision implementation and its documented preprocessing conventions [2, 3].
2.1.2 Federated Optimization
A coordinator distributes a global model to clients; each client optimizes on local data and returns an update. FedAvg combines client parameters with sample-count weighting. FedProx adds a local proximal penalty that discourages excessive movement from the global parameters when client data differs. These methods change optimization rather than the ResNet18 architecture.
2.1.3 Privacy Mechanisms
Federated data locality does not automatically protect model updates. Secure aggregation lets a coordinator recover a permitted aggregate while limiting visibility of individual unmasked contributions under protocol assumptions. Differential privacy separately bounds an individual record contribution through a specified mechanism, clipping, noise, sampling, and composition accounting. Transport security and application authorization address further boundaries.
2.1.4 Explainability and Evaluation
Grad-CAM highlights image regions associated with a model class score; it is not validated tumour localization or segmentation. Model performance also depends on class balance, source population, preprocessing, and independent splits. Accuracy is therefore accompanied by macro F1, balanced accuracy, per-class sensitivity and specificity, support counts, and explicit dataset limitations.
2.2 Existing System and Its Limitations
Centralized training simplifies pooled optimization but assumes raw data can be transferred and governed centrally. Isolated local models lose opportunities for shared learning. Plain federated updates reduce routine raw-image transfer while leaving update disclosure concerns. A standalone training script also lacks authenticated records, protected file access, and experiment provenance.
2.3 Proposed System Overview
PULSAR integrates role-specific React workspaces, validated FastAPI services, SQLite persistence, protected storage, strict ResNet18 inference, and a separate experiment worker. The coordinator communicates with three local clients for FedAvg/FedProx training. SecAgg+ masks permitted contributions before they cross the client-process boundary. Experimental DP-SGD separately clips and noises per-sample gradients with accounting.
The doctor workflow connects patient selection, protected image upload, classification, Grad-CAM, observations, and PDF reporting. Research views retrieve persisted configurations, metrics, failures, and artifacts rather than invented dashboard values.
2.4 Research Gap and Motivation
The contribution is an integrated implementation and verification workflow, not a new neural-network architecture. A consistent model and dataset contract supports traceable comparisons, while application authorization connects experiments to a usable research interface. Data locality, aggregate visibility, and differential privacy are treated as distinct properties with separately documented limits.

3.2 System Architecture
The application architecture separates browser interaction, API services, persistence, protected file storage, model inference, and long-running training. Training experiments are placed in a persistent SQL queue. A separate Python worker claims jobs and invokes the shared PyTorch training engine. The worker writes round metrics, results, checkpoints, and failure states to the database and experiment artifact directories. This design prevents a long-running training task from blocking an ordinary API request.

3.3 Module Description
3.3.1 Authentication and Account Management
Authentication and account management provide two application roles: Admin and Doctor. Login and logout use revocable opaque sessions. Passwords are stored using a password-hashing mechanism; session and role/status checks are enforced by backend dependencies. The application does not use JWTs stored in localStorage as its documented authentication approach.
The Admin workspace supports doctor account management, including creating, updating, activating or deactivating accounts, and resetting doctor passwords. Admins can inspect aggregate application statistics, experiment records, model comparisons, and privacy evidence. Admin permissions do not grant access to patient scans or individual patient records through the application.
3.3.2 Patient Records and Doctor Ownership
The Doctor workspace supports patient registration and record management. Doctors can search, filter, sort, and page through their records, update patient details, and record visits and follow-ups. The ownership model assigns a patient record to one doctor. Backend checks enforce ownership when a doctor requests a patient, image, analysis, or report.
Patients are not application users and cannot sign in. The system does not include patient, nurse, or receptionist roles. These boundaries simplify the current role model and prevent the report from implying workflows that are not implemented.
3.3.3 Persistence and Reporting
SQLite stores persistent users, sessions, patients, visits, analyses, reports, experiment records, and round metrics through SQLAlchemy. Alembic manages schema changes. Images, heatmaps, reports, and experiment artifacts are stored as protected files with corresponding records. A generated PDF represents a snapshot of the analysis and doctor review. Later edits do not silently rewrite an already generated report [1, 10, 11].
The browser uses authorized API endpoints rather than direct database or filesystem access. A Doctor can retrieve owned patient resources; an Admin can manage doctor accounts and inspect aggregate experiment information, but cannot use Admin permissions to read patient scans.
3.3.4 Image Analysis and Explainability
The upload module accepts PNG and JPEG with extension, MIME, content, size, and dimension checks. It decodes and re-encodes files before protected storage; the configured upload limit is 10 MiB. Authorized endpoints enforce ownership for images and derived artifacts.
Inference loads approved.pt, version centralized-verification, through strict architecture, class-mapping, normalization, and preprocessing validation. Invalid checkpoints cause an explicit error rather than a silent substitution of legacy or random weights. Analyses persist class probabilities and model version/hash metadata.
Grad-CAM is generated from the ResNet18 layer4 feature maps and gradients for a selected class score. It creates a heatmap overlay that can help a user inspect which image regions contributed to that score. The visualization does not constitute tumour segmentation, lesion localization, or clinical proof.
3.3.5 Model and Preprocessing Contract
The active checkpoint records 64 by 64 RGB input, bilinear square resizing, ImageNet mean [0.485, 0.456, 0.406], and standard deviation [0.229, 0.224, 0.225]. It uses standard BatchNorm ResNet18 with 11,178,564 trainable parameters. The shared implementation also supports other configured resolutions and a GroupNorm variant for privacy-related experiments, without introducing another classifier family [1, 3].
The application does not use the retired clinical-tabular fusion or MobileNetV2 fallback paths. Doctor-entered history and observations remain record information, separate from image class probabilities.
3.3.6 Federated Learning and Experiment Tracking
Centralized training, FedAvg, and FedProx use a shared ResNet18 training engine. Reproducible non-IID partitions can give Hospital A, B, and C different class distributions. In the recorded full-data seed/alpha setting, client training counts are 198, 233, and 75. Different seeds or Dirichlet alpha values can produce different partitions.
FedAvg performs sample-weighted parameter averaging. FedProx adds a proximal local-loss term to limit drift from global parameters. Configurations and round metrics record how each experiment was actually trained.
A separate worker claims experiments from a SQL-backed queue and persists status, metrics, checkpoints, failures, and artifacts. The documented setup uses one worker. Completed and invalidated historical records remain distinguishable, so unsuitable runs are not silently presented as valid evidence.
3.3.7 Secure Aggregation and Differential Privacy
Secure aggregation and differential privacy are implemented as separate mechanisms. Flower SecAgg+ is integrated into the federated workflow with a cryptographic PRG adapter. The protocol is designed so that the coordinator obtains an aggregate contribution without directly reading each individual unmasked client update, under the documented assumptions. Tests cover weighted reconstruction, masked payload visibility, fresh masks, seed/domain separation, dropout, malformed or replayed messages, and corrupted encrypted shares.
The DP-SGD module uses Opacus to support per-sample gradient handling, gradient clipping, Gaussian noise addition, and Rényi Differential Privacy accounting. The documented implementation is experimental and limited to the specified update mechanism. Its scope must not be described as a complete end-to-end privacy guarantee for all records, outputs, logs, or application data.
Secure aggregation protects individual-update visibility under its protocol assumptions; DP-SGD addresses the influence of examples in its accounted mechanism. Neither replaces protected transport, storage controls, or access checks. The simulation excludes shared-host administrators and client collusion from its protection claim, and production privacy governance remains future work.

4.2 Implementation Methodology
4.2.1 Dataset and Checkpoint Validation
The dataset workflow is an important part of the experimental design. The README documents byte-level and pixel-level hashing, duplicate grouping, reproducible split manifests, and audit checks intended to identify duplicate images and prevent exact duplicate overlap across train, validation, and test splits. Older model artifacts affected by dataset leakage or incompatible metadata were excluded from the active inference path.
The active model is a ResNet18 architecture with a four-class output head. Model checkpoints include metadata required to reconstruct and validate the model, including class mapping and preprocessing. The inference service uses strict loading so that a checkpoint with incompatible metadata or label mapping fails rather than being silently accepted.
The manifest links source paths, labels, hashes, groups, splits, and optional patient/study identifiers. Source hashes and split isolation are checked before training. A stored manifest digest links checkpoint provenance to the evaluated data boundary.
4.2.2 Training and Model Selection
The shared engine validates configuration, seeds training components, constructs ResNet18, and creates training and validation loaders. It performs real optimizer steps and records loss, accuracy, macro F1, and duration. Early stopping and best-checkpoint selection use validation performance. The selected checkpoint records architecture, ordered labels, normalization, preprocessing, algorithm, configuration, and manifest provenance.
The selected checkpoint uses BatchNorm; configured DP/secure experiments can use GroupNorm. Strict loading rejects incompatible weights and mappings. Model approval means research-checkpoint selection, not medical approval.
4.2.3 Federated Local Objectives
For client k with n_k examples, FedAvg forms a sample-weighted global model: w_next = sum_k (n_k / sum_j n_j) w_k. FedProx adds (mu / 2) times the squared distance from the received global parameters to each local loss. This proximal term addresses local model drift under heterogeneous client data; it does not encrypt an update.
4.2.4 Secure Aggregation and Experimental DP SGD
In the secure workflow, the Flower SecAgg+ stages coordinate key setup, masked update upload, and aggregate reconstruction. A cryptographic pseudorandom generator adapter expands protocol material into masks. The client modifier masks model arrays inside the client process and clears the unmasked array records before the reply crosses the process boundary. The coordinator strategy receives the reconstructed weighted aggregate, not the individual unmasked client models.
The documented threat model is limited. The clients share a host; a host administrator is outside the protection boundary; client collusion is not covered; and independent multi-host deployment has not been validated. These constraints must accompany any description of the secure aggregation feature.
The secure configuration registers three clients, requires at least two contributors, and uses a two-of-three reconstruction threshold. Protocol evidence records completed stages, responder counts, contributor counts, quantization configuration, duration, and serialized message sizes. Secret keys, raw reconstruction payloads, and masked vectors are not exposed as public audit artifacts [1, 4, 5].
The cryptographic adapter uses ChaCha20 and HKDF to expand domain-separated protocol material into masks. Unmasked arrays are cleared in the client process before a reply crosses the process boundary. Public counts, timing, global model parameters, and aggregate validation results remain visible [8, 9].
Opacus DP-SGD applies per-sample gradient clipping and Gaussian noise with cumulative RDP accounting. A recorded two-round full-data experiment used noise multiplier 1.1, clipping norm 1.0, and delta 0.00001. Its per-client epsilon values are mechanism-specific; they are not a patient-level budget or a budget for the whole application [1, 6, 7].
Private partition construction, patient-level composition, held-out evaluations, application records, and cross-experiment releases are outside that accountant scope. The full-data DP run used plaintext aggregation. Combined secure FedProx with DP was tested separately on a small repository-data subset as integration evidence.

CHAPTER 5  CONCLUSION AND FUTURE SCOPE
5.1 Conclusion
PULSAR demonstrates an integrated research prototype for lung image classification and privacy-aware federated learning experimentation. The system combines a ResNet18 image classifier, Grad-CAM visualization, doctor-managed patient records, protected file handling, PDF reports, centralized and federated training, secure aggregation integration, experimental DP-SGD, and persistent experiment tracking.
The implementation uses a single ResNet18 architecture with a four-class output head. Centralized training, FedAvg, and FedProx are training approaches that use this common model family. Three simulated hospital clients perform local optimization on non-IID partitions. Flower SecAgg+ provides a secure aggregation workflow under a limited documented threat model, while Opacus supports an experimental DP-SGD mechanism with per-sample processing and RDP accounting.
The selected inference checkpoint achieved 75.68% accuracy, with 84 correct classifications among 111 held-out images. This result is specific to the documented test set and does not establish clinical diagnostic accuracy or individual patient certainty. A separate one-round secure verification experiment recorded 36.04% accuracy; it is not the active model's accuracy, and DP was disabled in that run.
The project also demonstrates application-level controls through Admin and Doctor roles, doctor-owned patient records, protected image and report retrieval, and experiment persistence. The recorded backend, browser, build, lint, and dataset-audit results provide evidence of local software verification. However, the clients are simulated on one machine, the privacy mechanisms have documented limits, and the model has not undergone external clinical validation.
Overall, the project meets its research-prototype objective by implementing and testing a connected application and federated learning workflow while documenting what remains unverified. It should be presented as a technical research and educational system, not as a clinically approved diagnostic tool.
5.2 Future Scope
Future work should first strengthen dataset quality and evaluation. The project requires trusted patient/study identifiers, source and modality metadata, patient-independent grouped evaluation, review of related or near-duplicate scans, external dataset testing, uncertainty intervals, calibration analysis, and clinically meaningful error analysis. Model selection should use validation metrics, with test data reserved for final evaluation.
Predictive performance can be investigated through controlled experiments using justified augmentation, larger input resolution, pretrained initialization, learning-rate schedules, class-imbalance analysis, and hyperparameter search. Such changes must be trained and evaluated before any improvement is claimed. Centralized, FedAvg, FedProx, secure, and DP experiments should be compared under matched initialization, preprocessing, optimization budgets, data splits, and multiple random seeds where practical.
Federated deployment can be extended from local simulation to independently administered hosts. This requires authenticated inter-client transport, deployment and dropout testing across machines, concurrency and operations design, and independent review of the SecAgg+ integration and cryptographic PRG adapter. Stronger threat models may need to address client collusion and malicious servers.
The differential-privacy implementation requires production-grade randomness, an explicitly justified privacy unit, complete release and composition accounting, and a documented policy for all model releases and outputs. The project also requires PostgreSQL integration testing if a server database is adopted, TLS, at-rest encryption, backup and restore procedures, retention policies, identity/MFA controls as required, and a review of dataset and software licenses.
Finally, any move toward clinical use would require expert evaluation, appropriate institutional governance, regulatory assessment, usability testing, and prospective validation. Until those activities are completed, the application should remain a research prototype and should not be used to make independent patient-care decisions.

One-versus-rest ranking measure over decision thresholds where defined.
